# pm

プロジェクトの困りごとを聞いて**見立てと助言**を出し、その判断に効く資料だけを作りながら状況を整理する。

資料を作ること自体は目的ではない。「何を可視化すれば、どの判断ができるようになるか」から資料を選ぶ。
助言だけで足りるなら資料は作らない。全 46 種を揃えようとしない（テーラリング）。

## 決定的な作業は script に任せる

以下 `PM="node ${CLAUDE_SKILL_DIR}/scripts/pm.mjs"`（この SKILL.md があるディレクトリ基準）とする。
シェルの変数は呼び出しをまたいで残らないので、Bash を呼ぶたびに先頭で `PM=...;` を定義する。
script は読解・書き換え・再実装せず、そのまま実行する。

| コマンド | 用途 |
|---|---|
| `$PM phases` | タイミング A〜J と、よくある状況・中心の資料 |
| `$PM list [--phase A,B] [--core]` | 資料カタログ（id・タイミング・名前・判断したいこと・計算の有無） |
| `$PM new <id>... [--dir D] [--project NAME]` | テンプレートから資料を作る。既にある資料は上書きしない |
| `$PM sync [--dir D]` | 計算ブロックの再計算・更新日の反映・目次 `README.md` の再生成 |
| `$PM status [--dir D]` | 作った資料と残 TODO・要確認の数 |
| `$PM check [--dir D] [--render]` | TODO の残り・計算の古さ・コードブロックの閉じ忘れを検査。`--render` で Mermaid を実際に描画して確かめる |

既定の置き場所は `docs/pm/`。プロジェクトに既存の置き場所（`docs/adr/` など）があれば `--dir` で合わせる。

## 手順

### 1. 状況をつかむ（聞く前に調べる）

コマンドはまとめて 1 回で打つ:

```bash
$PM status; $PM phases
git log --oneline --since="4 weeks ago" | head -30
gh issue list --limit 30 2>/dev/null; gh pr list --limit 30 2>/dev/null
```

加えて、会話の流れ・README・既存のドキュメントを読む。ユーザーに聞くのは、調べても分からないことだけにする。

### 2. 見立てる

依頼を次の 3 つのどれか（複数可）として読む:

- **困りごとの相談**（「うまく行ってない」「進捗が見えない」など）: [references/diagnosis.md](references/diagnosis.md) を読み、当てはまる症状を 2〜3 行拾って原因の仮説を立てる。仮説を確かめるのに必要なら、質問を 1 回に 3 つまでで聞く
- **タイミングの指定**（「立ち上げる」「リリース前」など）: `$PM phases` の段階に当てはめる。立ち上げつつ範囲も決める、開発中に変更と品質の問題が同時に来る、のように**複数の段階にまたがってよい**
- **判断したいことが明確**（「リリースしていい？」「どの技術にする？」）: `$PM list` の「判断したいこと」の列から資料を引く

どれとも読めないときだけ、`$PM phases` の一覧を見せて「今どんなタイミング？困っていることがあればそれでもいい」と聞く。

### 3. 助言し、作る資料を示してすぐ始める

最初の返答で次を出す:

1. **見立て**: 何が起きていて、なぜそうなっていそうか（根拠にした事実を添える）
2. **今日からできる助言**: 資料が無くてもできる行動を 1〜3 個
3. **作る資料**: 優先順に、原則 5 つまで。各資料に「これで何が判断できるようになるか」を 1 行。カタログの「中心」は目安で、段階をまたいで選んでよい

資料の作成はユーザーの返事を待たずに始める（「以下を作りながら状況を整理する」）。ユーザーが資料を要らないと言った、または助言だけで足りる相談なら作らない。

### 4. 資料を作って埋める

```bash
$PM new <id>... --project "<プロジェクト名>"
```

作った資料の段階の references だけを読む（`references/phases/<A〜J>.md`。例: 01 と 04 なら A.md と B.md）。各資料について:

- 手順 1 で調べた事実から埋める。references の「先に調べる」に挙がったものは聞く前に調べる
- 分からないことはまとめて聞く（1 回に 3 つまで）。答えが出ないものは数字や名前を作らず `要確認: <問い>` と書く
- テンプレートの見出し・表の形・`<!-- pm:... -->` の行は消さない。使わない行は消してよい
- 計算あり（11・12・19・27・34・35）は `pm:calc` の表だけを埋める。結果・図は `sync` が書くので手で書かない
- 既にある資料は上書きせず、その場で更新する。ADR は新しい決定を上に足す

### 5. 検査する

```bash
$PM sync && $PM check
```

- `FAIL` 行は指示どおり直して、もう一度 `check` する。`TODO` は埋めるか `要確認:` に書き換える
- `ASK` 行（要確認）は失敗ではない。最後にユーザーへの問いとして渡す
- Mermaid を書き換えた・自分で図を足したときは `$PM check --render` で描画まで確かめる（初回は mermaid-cli を npx で取得する。ネットワークが無い環境では省略してその旨を伝える）

### 6. まとめて渡す

最後の返答は次の順で短く:

1. **見えたこと**: 資料を作って分かった判断の材料（例: クリティカルパスは A → C → D で 8 日、など）
2. **次の一手**: 誰が何をするか、1〜3 個
3. **要確認**: `ASK` の問いを箇条書きで（ユーザーが答えればすぐ資料に反映できる形で）
4. **資料**: 目次 `docs/pm/README.md` のパス

続けて見直すと良い時期や、次に効きそうな段階の資料があれば 1 行で添える。

## こういうときは

| 状況 | 対応 |
|---|---|
| git リポジトリでない / gh が使えない | その情報は飛ばし、会話とファイルだけで見立てる。失敗したコマンドを繰り返さない |
| node が無い | 資料は作らず、見立てと助言だけを返す。資料が必要なら Node.js 18 以上を入れるよう伝える |
| ユーザーがすぐ答えられない・質問に答えない | 待たずに進め、分からない所は `要確認:` に残す |
| `docs/pm/` 以外に既存の PM 資料がある | 二重に作らない。既存の資料を読んで見立てに使い、足りない資料だけ `--dir` で同じ場所に作るか、ユーザーに置き場所を聞く |
| 相談が PM ではなく実装・不具合修正の依頼だった | この skill の手順は使わず、その依頼として扱う |

## 守ること

- 数字・人名・日付を作らない。根拠が無いものは `要確認:` にする
- 資料の量で頑張らない。判断に使われない資料は作らない
- 個人を責める書き方をしない（原因は仕組みで捉える）
- 今の詰まりを 1 枚の図で見たいだけなら status-board skill、タスクをチケットに落とすなら local-ticket-system skill の方が合う。そう伝えてよい
