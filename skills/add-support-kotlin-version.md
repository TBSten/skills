# Add/Remove Supported Kotlin Version Skill

[日本語](./add-support-kotlin-version.ja.md)

A [Claude Code](https://docs.anthropic.com/en/docs/claude-code) skill that adds or removes a specific Kotlin version from a Kotlin Compiler Plugin project's support matrix.

## Quick Start

### 1. Install the skill:

```bash
gh skill install tbsten/skills add-support-kotlin-version
```

### 2. Ask your AI agent:

```
Add Kotlin 2.4.0 support to this compiler plugin project.
```

## What This Skill Does

For compiler plugin projects that already have multi-version support infrastructure, this skill:

1. Decides whether the target Kotlin version fits an existing compat module range, requires a reflection-based shim, or warrants a brand-new compat module
2. Adds the new compat module via the `delegation` pattern (`CompatContext by k230.CompatContextImpl()`) so each module stays ~10–30 lines
3. Updates the **SSOT** (`scripts/supported-kotlin-versions.txt`), which drives the dynamic CI matrix (`fromJSON`), kctfork version selection, version catalog, and README
4. Hooks new feature flags into the `CompatContext` SPI (capability flags) so the plugin **degrades gracefully** on older Kotlin instead of failing to load
5. Runs the per-version test script across every entry in the SSOT to verify

## Supported Architectures

### A: Compat Module Layer (metro-style with capability flags)

Projects with `compiler-plugin/compat-kXX/` modules, packaged into a ShadowJar with `mergeServiceFiles()`. ServiceLoader dispatches to the best-matching `CompatContext` implementation at runtime, ranked by `KotlinToolingVersion` (Maturity-aware: STABLE > RC > BETA > ALPHA > MILESTONE > DEV > SNAPSHOT).

`CompatContext` exposes two kinds of members:

- **API shims** — methods whose JVM signature differs across versions (e.g. `irCall(IrBuilderWithScope, ...)` receiver widening). Each compat module compiles against its own baseline so the generated bytecode lines up at runtime.
- **Capability flags** — `supportsFirHintGeneration()`, `supportsFirCheckers()`, `supportsKlibCrossModuleHint()` etc. These let the main plugin **skip registering extensions** on older Kotlin instead of crashing the FIR session.

### B: Source Set Separation

Projects with `src/v2_0_0/kotlin/` or `src/pre_2_0_0/kotlin/` directories. Gradle dynamically includes the appropriate source directory based on the Kotlin version at build time.

Best for absorbing K1 (PSI/ComponentRegistrar) vs K2 (FIR/CompilerPluginRegistrar) divergence.

## Key Concepts

### Delegation pattern for new compat modules

```kotlin
class CompatContextImpl : CompatContext by K230Impl() {
    override fun supportsFirHintGeneration(): Boolean = true   // diff only
    override fun supportsFirCheckers(): Boolean = true

    class Factory : CompatContext.Factory {
        override val minVersion: String = "2.3.20"
        override fun create(): CompatContext = CompatContextImpl()
    }
}
```

A new compat module is needed only when:

- The target version falls outside all existing ranges, AND
- The change cannot be absorbed via a `compat/`-level reflection shim (e.g. `IrDeclarationOriginCompat`), AND
- `NoSuchMethodError` / `NoClassDefFoundError` / `IncompatibleClassChangeError` occurs that calls for an actual binary boundary

### SSOT-driven CI matrix

```yaml
resolve-supported-kotlin-versions:
  outputs:
    list: ${{ steps.read.outputs.list }}
  steps:
    - uses: actions/checkout@v4
    - id: read
      run: |
        list=$(grep -vE '^[[:space:]]*(#|$)' scripts/supported-kotlin-versions.txt | jq -R . | jq -sc .)
        echo "list=$list" >> "$GITHUB_OUTPUT"

compiler-plugin-test:
  needs: resolve-supported-kotlin-versions
  strategy:
    fail-fast: false           # critical — keeps stable results visible when Beta/RC fail
    matrix:
      kotlin: ${{ fromJSON(needs.resolve-supported-kotlin-versions.outputs.list) }}
  steps:
    - run: ./scripts/compiler-plugin-test.sh "${{ matrix.kotlin }}"
```

Add one line to `scripts/supported-kotlin-versions.txt` → the matrix expands automatically.

### Baseline vs runtime, and test classpath isolation

The main `compiler-plugin` module is compiled against **one** baseline Kotlin (= `libs.versions.kotlin`). API drift outside `CompatContext` will surface as `NoSuchMethodError` at runtime, which the skill tracks.

For per-version testing, `force` resolution must be scoped to `testCompileClasspath` / `testRuntimeClasspath` only — applying it broadly breaks KGP's own buildtools class initialization. Set `-Xskip-prerelease-check -Xskip-metadata-version-check` on `compileTestKotlin` only when `testKotlinVersion != baseline`.

### kctfork version mapping

```kotlin
val kctforkVersion = when {
    testKotlinVersion.startsWith("2.1") -> "0.10.0"           // 2.2+ K2JVMCompilerArguments diff
    testKotlinVersion.startsWith("2.4") -> "0.13.0-alpha01"   // 2.4 API changes
    else -> libs.versions.kctfork.get()
}
```

The kctfork test JVM must run on Java 21 (`javaLauncher.set(...)`) — kctfork bundles a Kotlin compiler that cannot parse JDK 26 version strings.

### `fail-fast: false` in CI

Setting `fail-fast: false` in the GitHub Actions matrix is critical — it ensures stable-version test results are visible even when experimental/RC versions fail.
