# setup: アプリにフィードバックモードを入れる

**読むのはこのファイルと、選んだ adapter のファイル 1 枚だけ**（`adapter.md` §2 の表）。仕様（`references/spec/`）は、手順の中で指したところだけ読む。

> 導入先のコードを変えるので、§1 の手順 1〜3 で作る plan（debug 限定の方法・adapter・Sink・optional の選択）を、書き込む前に人に示して承認を取る。

## 1. 手順

1. **調べる**: アプリの種類と UI 層（DOM の有無）・ビルドの種類（debug / release、環境変数）・テストと確認のコマンド・ヘッドレスで動かす方法・正本 docs（README・`CLAUDE.md`）・`.gitignore`・置き場になりそうな場所。`scripts/detect.sh` の出力の「5. 既存のデバッグ基盤」「6. 既存のログ基盤」も見る。
2. **plan を作る**（ここまで書き込まない）:
   - **adapter**: `adapter.md` §2 から 1 つ選び、そのファイルを読む。無ければ §3 の手順で作る。
   - **既存のデバッグ基盤**（§3）: あれば入口と本番除外をそれに乗せる。
   - **debug 限定**（§2）: どのビルドに入れるか・どう外すか・外すものの一覧・検査のコマンド。
   - **Sink と置き場**: 既定はローカルのファイル（`references/spec/transport.md` §2）。Inbox・Archive・添付置き場の場所（`references/spec/data.md` §2）。
   - **optional**: `references/spec/features.md` §2 から入れるものを選ぶ（迷ったら O1 スクリーンショットだけ）。
   - **ログ**（§4）: 既存の基盤を読むか、差し込み口だけ置くか。
   - 決めたことを、下の形で 1 画面にまとめて人に示す（コードはまだ書かない）。

     | 項目 | 書くこと |
     |---|---|
     | adapter | 選んだ adapter と、そのファイルの検証状況 |
     | 入口 | 既存のデバッグ基盤があれば、その基盤に足す 1 項目だけ（ホットキー・FAB は足さない）。無ければ新しく作る入口 |
     | 本番から外す | ビルド時に消す方法・実行時の保険・本番の成果物を検査するコマンドと CI。既存の基盤に乗るなら「その基盤が本当に外れているかを最初に確かめる」 |
     | 受け口と Sink・置き場 | Inbox・Archive・添付の場所、git に入れるか |
     | ログ | 何を `getRecentLogs` で読むか。**ログ基盤の変更・拡充は別タスクにする**と書く |
     | 部品の名前 | どこから `data-fb` などを付けるか |
     | optional | 入れる機能（`features.md` §2 の番号） |
     | 変えるファイル | 導入先で足す・変えるファイルの一覧 |
     | 確認したいこと | 人に決めてもらうこと（1〜3 個） |
3. **承認をもらう**。
4. **コアを置く**: `bash "${CLAUDE_SKILL_DIR}/scripts/copy-core.sh" <導入先の dev 専用ディレクトリ>`。`core/` に Sink・組み立て・HTTP の受け口・テストをコピーし、`node --test` が通ることを確かめる（36 件 + 1 件 skip）。script は読解・書き換え・再実装せず、そのまま実行する。既存ファイルがあれば中断するので、上書きは `--force`。TypeScript の導入先は `assets/templates/core-ts/`（型付きの Sink と vitest の契約テスト 32 件）を手でコピーしてもよい。Node が無い受け口は `adapter.md` §3 の 3。
5. **adapter を置く**: adapter のファイルの「差し込み口」の表どおりに、ひな形をコピーして埋める（受け口・画面側・`entry`・`collect`・`transport`・`pointer`）。送信先の URL・鍵は開発用のビルド変数から渡す（既定値を持たない）。
6. **部品に名前を付ける**: 主な 20〜30 箇所から付け始め、以後フィードバックが来た部品から増やす（`features.md` R5）。
7. **ログを繋ぐ**: `getRecentLogs` を既存の基盤に繋ぐ（§4）。
8. **確かめる**（ヘッドレス・偽データ・一時ディレクトリ）: 入る → 部品にホバー（タップ）→ 選ぶ → 書く → 送る → Inbox に記録ができる → 下の要素にクリックが届いていない → 出る。スクショを入れたなら、枠と切り抜きが合っているか、撮れないときに理由が出るか。**本番ビルドを作って検査 script で何も残っていないこと**を確かめる。
9. **loop 側を置く**: `references/loop/loop.md` §0 の置き換え表を導入先の値で埋め、導入先の運用 docs（または `.claude/skills/feedback-loop` 相当）にする。`CLAUDE.md` に「置き場の場所・オーケストレータは受付だけ・対応はサブエージェント」を 1〜2 行足す。
10. **試しに 1 件通す**: 実際に 1 件送り、loop の手順で対応して archive まで通す。
11. **正本 docs に書く**: 入り方・節と既定・置き場の場所・名前の規則・debug 限定にした方法と検査コマンド・既知の制約。

## 2. debug ビルドだけに入れる

フィードバックモードはスクショ・ログ・画面の状態を集めて送る開発用の道具なので、本番には入れない。

- **外すもの**: コード・UI（モード・吹き出し・FAB・メニュー項目・ホットキー）・送信先（URL・鍵・ポート。ビルド変数にも）・依存（スクショのライブラリなど）・権限と設定（スクショ・ネットワークの許可、Android の cleartext、iOS の ATS 例外、CSP の `connect-src`）・受け口（開発用サーバ・IPC ハンドラ）。
- **三重に守る**: (1) ビルド時に消す（DCE + 動的 import・別 entrypoint・debug source set）が主。(2) 実行時の `enabled` / debug 判定は保険。(3) 本番の成果物を `bash "${CLAUDE_SKILL_DIR}/scripts/check-no-feedback-in-prod.sh" <成果物>` で検査し、CI に入れる（script はそのまま実行する。パターンは導入先の識別子に合わせて足してよい）。
- 環境ごとの消し方は adapter のファイルの「本番から外す」。
- 本番のユーザ向けに**意図して**入れたい場合は別の判断（同意・個人情報・送信先・保存期間・鍵の持ち方・ストア審査）。この skill のひな形はその用途を想定していない。

## 3. 既存のデバッグ基盤に乗せる

アプリにすでに debug menu・開発者設定画面・dev panel・dev toolbar・隠しジェスチャ・feature flag の画面があれば、**新しい入口もガードも作らず**、その入口に「フィードバックモードへ」を 1 つ足し、その基盤の本番除外に乗る。

- 探し方: `detect.sh` の「5.」と、grep（`debugMenu`・`DevMenu`・`DevSettings`・`dev panel`・`devtools`・`isDev`・`__DEV__`・`kDebugMode`・`BuildConfig.DEBUG`・`#if DEBUG`・`import.meta.env.DEV`・`shake`・`onLongPress`）。環境ごとの例は adapter のファイル。
- 乗せる前に確かめる:
  1. その基盤が本当に本番から外れているか（成果物を grep。feature flag だけで隠している基盤はフラグ次第で本番に出る）。**外れていなければ、乗せずに人に指摘して確認する**。
  2. 足したコードが基盤の外に静的 import で残らないか。
  3. 基盤の UI の決まり・アクセスの条件（社内ビルドだけ・QA だけ）に合わせる。
  4. 基盤がスクショ・ログのバッファ・環境情報・バグ報告の送信先を持っていれば、`capture`・`logs`・`getEnv`・Sink として再利用する。
  5. 基盤のメニューを閉じてからモードに入るか（全面オーバーレイと衝突しないか）。
- 見つかっても §2 の「外すものの一覧」と検査は省かない。
- 最小例: `assets/templates/adapters/desktop/electron/electron-dev-menu.mjs`（Electron の開発メニュー）、`references/setup/web/dom.md` の `entry`（既存の dev panel から `enter()`）。

## 4. ログ

**フィードバックモードはログを読んで添付するだけ**にする。ログの収集・形式・保存・ローテーション・圧縮・一次の redact・本番での扱いは、別タスク（別 plan・別 PR）にする。理由: ログは本番でも要る（フィードバックは debug 限定）・動き方と変更の頻度が違う・個人情報と容量の論点が別。

- **既存のログ基盤がある**: `getRecentLogs` でそのバッファ・ファイルの末尾を読む。ログの形が分かる案内を `pointer` に書く。新しいログの仕組みをフィードバック側に作らない。
- **無い**: 差し込み口（`getRecentLogs` / `logEvent`）だけ置き、ログ節は空でよい。暫定が要るなら `assets/templates/adapters/web/dom/log-buffer.example.js`（Web の console のフック。本番に持ち込まない）。
- フィードバックの価値の多くはログで決まる。画面操作（クリックした部品の道筋）・API / IPC の呼び出しと結果・状態の変化・エラーが 1 か所に集まっていないと、記録から原因をたどれない。足りなければログ基盤の別タスクで補う。
- 組み立て側が持つのは、新しい方から 200KB までの件数制限・error/warn の要約・最後の redact だけ（`references/spec/data.md` §3.3）。
