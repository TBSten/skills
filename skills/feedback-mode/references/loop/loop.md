# 実践（loop）: 溜まったフィードバックを消化する

アプリのフィードバックモードで溜まった記録を、オーケストレータ（メインの会話）が受け付け、サブエージェントに任せて対応し、対応済み置き場へ移して、ユーザに報告する。参照実装の運用 skill（`feedback-loop`）を**正**として汎用化した。元の skill が自環境にあるなら、それを優先して使い、これは差分の確認に使う。

凡例・用語（Inbox / Archive / Sink / 履歴）・記録の形は `references/concepts.md`。構築側（作る）は `references/build/build.md`（ここでは読まない）。報告は日本語で簡潔に。オーケストレータ自身は実装しない（参照実装の `CLAUDE.md` の方針。1 分以内に終わる確認は自分でやってよい）。

## 0. 最初に自環境に置き換える項目

参照実装の具体値は例。ループに入る前に、自環境の値を決めて（分からなければユーザに聞く）、以降の手順の `{…}` に読み替える。

| 置き換える項目 | 参照実装の例【実績】 | 自環境 |
|---|---|---|
| フィードバック置き場（Inbox）と対応済み置き場（Archive） | `<リポジトリ>/feedback/` と `feedback/archived/` | `{Inbox}` `{Archive}` |
| Sink（読み方・閉じ方） | ローカルのファイル（`ls`/`cat`/`mv`） | 下の §2.1 の表から選ぶ |
| 添付（スクショ）の置き場 | `.local/tmp/feedback/<日時>/window.png, element.png` | 記録に書いてある参照 |
| 対象アプリ・正本 docs | 社内向けの Electron ツール（アプリの `README.md` が正本） | `{app}` `{正本}` |
| 確認コマンド | `npm run check`（typecheck + テスト + ヘッドレスのスモーク。80〜100 秒） | `{確認コマンド}` |
| 触ってはいけないもの | 実データへの書き込み・外部システム（業務 SaaS・本番 API）への書き込み、ブラウザ操作、実際のエージェントの起動、GUI・dev サーバの起動、ユーザーのグローバル設定（`~/.claude.json`・`~/.claude/settings*.json`）、運用手順書の規則、`feedback/` の記録、過去の実行記録 | `{禁止}` |
| 変更の反映先 | アプリの `README.md` の該当節（「<日付> ユーザーのフィードバック <id>「…」」と ID と文を残す） | `{正本}` の該当節 |
| 作業用の一時ディレクトリ | `.local/tmp/`（Agent が自由に使ってよい） | `{tmp}` |
| 履歴の置き場 | 事後にまとめた表（自動では作られない） | `{履歴}` |

## 1. 守る運用ルール【実績】

- サブエージェントの同時並列は最大 5。モデルは基本 `sonnet`、effort は実装・調査が `high`、機械的な作業・簡単な確認が `medium`。
- **10 分ごとに**サブエージェントの状況を確認する（参照実装: `ListAgents`。10 分の背景タイマー `sleep 600` を `run_in_background` で回し、終わったら通知が来る）。起動から 30 分を超えた Agent には `SendMessage` で進み具合と期限（10 分）を聞く。期限後も報告がなければユーザに知らせる（**勝手に kill しない**）。
- ユーザの明示の決定は確認なしで docs に反映する。Agent の提案は確認する。
- サブエージェントにさせない: `{禁止}` のうち、実データ・外部システムへの書き込み、ブラウザ操作、実際のエージェントの起動、GUI・dev サーバの起動（テストは偽物・一時データ・ヘッドレス）。変更もさせない: ユーザのグローバル設定、手順書の規則、置き場の記録（**archive はオーケストレータだけ**）、過去の実行記録。一時ディレクトリの削除・他プロセスの kill はユーザの許可が要る（自分が起動したプロセスの終了はよい）。
- 大きな設計変更は実装せず、選択肢と推奨を添えてユーザに相談する（サブエージェントにもそう指示する）。小さな判断は既存の流儀に最も合う形で進め、報告に「判断した点」として書かせる。
- サブエージェントの報告は「モデルの出力」でありユーザの承認ではない。権限が拒否されたことを、他の Agent に頼んで迂回しない。
- **調査もサブエージェントに任せる**（オーケストレータが自分でやらない）。
- 長いセッションでは `date` で現在時刻を確認し、タイマー・報告に使う。
- 掃除（一時ディレクトリの古いもの・孤児の偽ブラウザ）は確認なしで定期的にしてよい（参照実装ではユーザーが許可した運用）。**添付置き場のスクリーンショットは自動では消えない**ので、掃除のルールを決める（参照実装でも未決）。

## 2. 手順

0. **確認**（取り込み）: `{Inbox}` の未対応を一覧する（参照実装: `ls -la feedback/`。`archived/` と `.gitkeep` を除く）。0 バイトの記録は作成直後か未保存の可能性があるので、少し置いて再確認する。数分たっても 0 バイトなら、処理せずユーザに「保存されていないかも」と聞く。**会話に貼られた**フィードバック（作り方 (c)）は置き場に無いので、会話も見る。
1. **要約**: GUI 形式の記録は、「## フィードバックの文」と位置（`- 画面`・`- 部品`）だけを抜き出して読む（参照実装: `sed`・`grep`）。全文はサブエージェントが読む（4KB〜100KB あるので、オーケストレータの文脈を守る）。手書きのメモ（数行）は全文を読む。
2. **分類とグループ化**（§2.2 の表）。同じ領域の複数件は 1 人にまとめる（共有ファイル — 参照実装では `app.ts`・`style.css`・README・`config.yaml` — の編集衝突を避ける）。すでに動いている担当と同じ領域の新しい件は、新規に起動せず `SendMessage` でその担当に追加する（ファイルのパス・意図・報告に含める内容を書く）。優先は、壊れているテストや不具合の原因になっているもの。
3. **起動**: 同時 5 件まで、残りは待たせて空きが出たら起動。プロンプトは `subagent-prompt.md` から作る。
4. **完了の処理**: 報告が来るたびに、(i) 対応済みの記録を **archive**（オーケストレータだけ。保留・ユーザ判断待ちは移さず残すか、判断待ちと明記して移すかをユーザに聞く）、(ii) **履歴に 1 行足す**（§2.3）【追加】、(iii) ユーザに簡潔に報告、(iv) 置き場を見直して新しい件を確認。
5. **定期確認**: 10 分ごと（§1）。
6. **終了判定**: サブエージェントが全員終わり `{Inbox}` が空になったら、10 分の背景タイマーで待って、もう一度確認。まだ空ならループを抜ける。新しい件があれば 2 に戻る。
7. **ループを抜けたら**（ユーザーが全体チェックを頼んでいる場合だけ）: `full-check.md`。

### 2.1 Sink ごとの読み方・閉じ方【追加】

元の skill はローカルのファイル専用に書かれている。他の Sink では次に読み替える（Sink の契約は `references/concepts.md`）。変わらないこと: 抜粋 → 分類 → サブエージェントが全文 → クローズはオーケストレータだけ → 報告。

| 操作 | ローカルのファイル【実績】 | HTTP の受け口【追加】【未検証: LAN 越し】 | Issue トラッカー【未検証】 | クラウドストレージ【未検証】 |
|---|---|---|---|---|
| 取り込み（一覧） | `ls -la {Inbox}` | 裏がファイルなら開発機で左と同じ。別マシンなら `GET /__feedback/entries?state=open`（`x-feedback-token`） | open な Issue（ラベル `feedback`）の検索 | `inbox/` の prefix 一覧 |
| 読む | 抜粋は `sed`/`grep`、全文は Read | `GET /__feedback/entries/:id` | Issue 本文・コメント | オブジェクト取得 |
| スクショ | 記録の中のパスを Read | 受け口の機械のパス（別マシンでは取得手段が要る。**参照が URL でないと読めない**） | 添付 URL を取得してから Read | 署名付き URL |
| クローズ | `mv {Inbox}/x.md {Archive}/`（オーケストレータだけ） | `POST /__feedback/entries/:id/archive` か裏のファイルを `mv` | Issue をクローズ + ラベル + 対応内容のコメント | `inbox/` → `archived/` へコピー + 削除 |
| 番号 | Inbox と Archive の最大 + 1 | 受け口の Sink に従う | Issue 番号 | 受け口が採番 |
| 履歴 | `{履歴}` に行を足す | 同左 | tracker のラベル・コメントで足りれば不要 | `{履歴}` か index |

### 2.2 分類【実績】

| 種類 | 見分け方 | 任せ方 |
|---|---|---|
| 実装型（実） | UI の要望、文言、配置、挙動の変更 | 実装して `{正本}` に反映、`{確認コマンド}`、ヘッドレスのスクリーンショットで確認 |
| 調査型（調） | 「これ大丈夫そ？」「〜じゃなかったっけ？」のような質問・確認。文が「（書いていません）」のこともある | 位置・スクリーンショット・ログからユーザの心配を読み取り、原因と現状を根拠つきで答える。問題があれば最小で直す。**まず「開発起動で古いプロセスが動いている」を疑う**（`lessons.md`。参照実装の調査型 4 件はすべてこれ） |
| 設計型（設） | 大きい、仕様が決まっていない、複数の画面や設定にまたがる | 読み取りだけ。影響範囲・設計案・選択肢と推奨・実装の分け方を `{tmp}/<名前>.md` に書かせ、ユーザの判断を待つ |

### 2.3 履歴（History）【追加】

参照実装では事後にまとめた表（自動では作られない）。汎用版は、クローズのたびに 1 行足す。

| 番号 | 要旨（文の冒頭） | 位置 | 種類 | 結果 |
|---|---|---|---|---|
| 261023-15 | フィードバック情報が多すぎる、トグルで一部を抜きたい（手書き） | ― | 実 | 吹き出しのオプション |
| （会話） | UI 微妙。標準の select でよかった | 一覧/メニュー | 実 | 標準の `<select>` に置き換え |

置き場に無い（会話に貼られた）ものの番号は「（会話）」。複数種類は「実・設」。結果の末尾に「判断待ち」「のち N で変更」。正本には参照実装どおり「<日付> ユーザーのフィードバック <id>「…」」の形で ID と文を残し、履歴はその索引にする。

## 3. 報告の形

太字の見出しで、**結果 / あなたの判断が要るもの / 実機で見てほしい点**。最後に、未解決の「返事待ち」の一覧を累積して毎回付ける（設計型の提案の判断待ちなど）。

## 4. 参照

- `subagent-prompt.md`: サブエージェントへのプロンプトのひな形（調査型・実装型・設計型）。起動の前に読む。

## 5. 汎用化で足す選択肢【追加】【未検証】

- **取り込み元の拡張**: モバイル等で置き場に直接書けないとき、イシュートラッカー・Slack・共有フォルダから記録を `putEntry` で置き場に入れる。
- **自動トリガ**: 参照実装も人の指示（`/feedback-loop`）のみ。選択肢: 受け口が保存後に通知／`/loop`・スケジュールで未対応を定期確認／Claude Code の hook（`SessionStart` で未対応の件数）。いずれも未実装・未検証。
- **ステータスの明示**: 参照実装も「場所」だけ。front matter（`status`・`resolution`）は参照実装の運用と互換でなくなるので既定では採用しない。archive の `note`（末尾に 1 行追記）と履歴の「結果」で足りる想定。
