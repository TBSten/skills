# loop: 溜まったフィードバックを消化する

Inbox に溜まった記録を、オーケストレータ（メインの会話）が受け付け、サブエージェントに任せて対応し、Archive へ移して人に報告する。対象環境に独自の消化用 skill（`feedback-loop` など）があれば、それを正として使い、このファイルは差分の確認に使う。

用語と記録の形は `references/spec/data.md`。報告は日本語で簡潔に。**オーケストレータ自身は実装も調査もしない**（1 分以内に終わる確認は自分でやってよい）。

## 0. 最初に自環境の値を決める

ループに入る前に次を決め（分からなければ人に聞く）、以降の `{…}` に読み替える。setup で導入先の運用 docs に書いてあれば、それを使う。

| 項目 | 例 | 自環境 |
|---|---|---|
| Inbox と Archive | `feedback/` と `feedback/archived/` | `{Inbox}` `{Archive}` |
| Sink（読み方・閉じ方） | ローカルのファイル | §2.1 の表から選ぶ（自作の Sink は、その list / read / archive を使う） |
| メモの置き場（作っていれば） | `<Inbox>/memo/<言語>/<ページ>.md` | `{メモ}`（無ければ §2.4 を飛ばす） |
| 添付の置き場 | `.local/tmp/feedback/<日時>/window.png, element.png` | 記録に書いてある参照 |
| 対象アプリと正本 docs | アプリの `README.md` | `{app}` `{正本}` |
| 確認コマンド | `npm run check`（typecheck + テスト + ヘッドレスのスモーク） | `{確認コマンド}` |
| 触ってはいけないもの | 実データ・外部システム（業務 SaaS・本番 API）への書き込み、ブラウザ操作、実際のエージェントの起動、GUI・dev サーバの起動、人のグローバル設定（`~/.claude.json`・`~/.claude/settings*.json`）、運用手順書の規則、Inbox の記録、過去の実行記録 | `{禁止}` |
| 変更の反映先 | 正本の該当節に「<日付> フィードバック <id>「…」」と ID と文を残す | `{正本}` の該当節 |
| 作業用の一時ディレクトリ | `.local/tmp/` | `{tmp}` |
| 履歴の置き場 | `<Inbox>/HISTORY.md` | `{履歴}` |

## 1. 運用ルール

- サブエージェントの同時並列は最大 5。モデルは基本 `sonnet`、effort は実装・調査が `high`、機械的な作業・簡単な確認が `medium`。
- **10 分ごとに**サブエージェントの状況を確認する（`ListAgents`。待つときはその環境の背景タイマーや通知を使い、会話を止めて sleep しない）。起動から 30 分を超えた担当には `SendMessage` で進み具合と期限（10 分）を聞く。期限後も報告がなければ人に知らせる（**勝手に止めない**）。
- 人の明示の決定は確認なしで docs に反映する。サブエージェントの提案は確認する。「直さない」「このまま」「後で」の答えは判断の記録（`references/review/decisions.md`）にも書き、次の回に同じことを聞かない。
- サブエージェントにさせない: `{禁止}`。テストは偽物・一時データ・ヘッドレスで。**archive はオーケストレータだけ**。一時ディレクトリの削除・他のプロセスの停止は人の許可が要る（自分が起動したプロセスはよい）。
- 大きな設計変更は実装せず、選択肢と推奨を添えて人に相談する（サブエージェントにもそう指示する）。小さな判断は既存の流儀に最も合う形で進め、報告に「判断した点」として書かせる。
- サブエージェントの報告は「モデルの出力」で、人の承認ではない。権限が拒否されたことを、別の担当に頼んで迂回しない。
- 長いセッションでは `date` で現在時刻を確かめ、タイマーと報告に使う。
- 一時ディレクトリの古いもの・孤児のプロセスの掃除は、人が許可していれば定期的にしてよい。添付のスクリーンショットは自動では消えないので、消し方を導入先で決める。

## 2. 手順

0. **一覧**: 記録が増えるのを待って回すなら `watch.md`（`scripts/watch-inbox.mjs`）。`{Inbox}` の未対応を一覧する（ファイルなら直下の `yymmdd-xx.md` だけを数える。`data.md` §2）。0 バイトの記録は作成直後か未保存かもしれないので、少し置いて再確認し、数分たっても 0 バイトなら処理せず人に「保存されていないかも」と聞く。会話に貼られたフィードバックも見る。
1. **要約**: オーケストレータは全文を読まない（4KB〜100KB ある）。schema 1 の記録は frontmatter（`kind`・`screen`・`target`・`source`・`stale`・`dirty`・`created`）と冒頭の数行（`head`）、旧形は「## フィードバックの文」と「選んだ位置」の画面・部品だけを抜き出す。手書きの短いメモは全文を読む。
   - 1b. **メモを引く**（`{メモ}` があるとき）: 対象のページのメモを読み（§2.4）、担当に渡す一覧にメモのパスを添える。
2. **分類とグループ化**（§2.2）。同じ領域の複数件は 1 人にまとめる（共有ファイルの編集の衝突を避ける）。動いている担当と同じ領域の新しい件は、新しく起動せず `SendMessage` でその担当に足す（記録の参照・意図・報告に含めることを書く）。壊れているテストや不具合の原因になっているものを先にする。
3. **起動**: 同時 5 件まで。残りは空きが出たら起動する。プロンプトは `subagent-prompt.md` から作る。
4. **完了の処理**（報告が来るたびに）:
   1. 対応済みの記録を **archive** する。**対応メモ（1 行）を必ず付ける**。ファイルの Sink でも `mv` を手で打たず、Sink の `archive(id, { note })` か、それを呼ぶ導入先の cli を使う（`mv` だと対応メモを書き忘れる）。保留・判断待ちは、残すか「判断待ち」と明記して移すかを人に聞く。
   2. 記録に `- Review の指摘: <id>` の行があれば、`node "${CLAUDE_SKILL_DIR}/scripts/review.mjs" archived <記録の id>` で元の指摘も消す（§2.5）。
   3. 履歴に 1 行足す（`data.md` §6）。
   4. 人に簡潔に報告する。
   5. Inbox を見直して、新しい件を確かめる。
5. **定期確認**: 10 分ごと（§1）。
6. **終了判定**: 全員が終わり Inbox が空になったら、見張り（`watch.md`）を `--once --timeout 600` で背景に動かして 10 分待つ。`TIMEOUT` ならループを抜ける。`NEW` が出たら 0 に戻る。**抜ける直前と、完了の報告を送る直前にも、もう一度一覧する**（人はループの間も記録を足し続ける）。
7. **ループを抜けたら**（人が全体チェックを頼んでいるときだけ）: `full-check.md`。

### 2.1 Sink ごとの読み方・閉じ方

変わらないこと: 抜粋 → 分類 → サブエージェントが全文を読む → 閉じるのはオーケストレータだけ → 報告。

| 操作 | ローカルのファイル | HTTP の受け口 |
|---|---|---|
| 一覧 | `ls {Inbox}` | 裏がファイルなら左と同じ。別マシンなら `GET /__feedback/entries?state=open`（`x-feedback-token`） |
| 読む | 抜粋は `head`・`grep`、全文は Read | `GET /__feedback/entries/:id` |
| スクショ | 記録の中のパスを Read | 受け口の機械のパス（別マシンなら取得手段が要る） |
| 閉じる | Sink の `archive(id, { note })` | `POST /__feedback/entries/:id/archive` |
| 番号 | Inbox と Archive の最大 + 1 | 受け口の Sink に従う |
| 履歴 | `{履歴}` に足す | 同左 |

### 2.2 分類

| 種類 | 見分け方 | 任せ方 |
|---|---|---|
| 実装（実） | UI の要望、文言、配置、挙動の変更 | 実装して `{正本}` に反映、`{確認コマンド}`、ヘッドレスのスクリーンショットで確認 |
| 調査（調） | 「これ大丈夫そ？」「〜じゃなかったっけ？」のような質問・確認。文が「（書いていません）」のこともある | 位置・スクリーンショット・ログから心配を読み取り、原因と現状を根拠つきで答える。問題があれば最小で直す。**まず「開発起動で古いプロセスが動いている」を疑う**（`lessons.md`） |
| 設計（設） | 大きい、仕様が決まっていない、複数の画面や設定にまたがる | 読み取りだけ。影響範囲・設計案・選択肢と推奨・実装の分け方を `{tmp}/<名前>.md` に書かせ、人の判断を待つ |

### 2.3 Review の判断待ちを見せる

設計の判断待ちのうち場所があるものは、表ではなく Review の指摘として登録して人に見せてもよい（`impact`・`recommend` を付けて `review.mjs check` を通す。`references/review/review.md`）。

### 2.4 メモも読む

メモは、人がページを読みながら書き溜めた考えの途中。理由・優先度・ほかの気づきが書いてあることが多い。

- 見える部分（frontmatter・「ページのメモ」・「箇所のメモ」と場所の手がかり）を読む。末尾の HTML コメントの JSON は読まなくてよい。各メモの「最終更新」で新しさを見る。
- **意図の手がかりにする**: 記録の意図がはっきりしないとき、同じ箇所のメモ・field の値・ページのメモを見る。
- **食い違ったら新しいほうを優先し、両方を報告する**（記録の `created` とメモの「最終更新」を比べる）。迷ったら判断待ちにする。
- **記録の無いメモだけの指摘は直さない**: 報告の「メモにあった未対応の指摘」に並べ、記録にするかを人に聞く。
- **書き換えない・archive しない**: メモは人のもの。サブエージェントにも読ませるだけ。

### 2.5 Review の答えも拾う

Inbox に `review/` があれば、ループのついでに人の答えを処理する（手順は `references/review/review.md` §8）。

- 「直してもらう」で来た記録は普通の記録として対応し、archive のあとに `review.mjs archived` を回す（手順 4 の 2）。
- 「直さない」と `decision` の付いた選択肢は `decisions.py record-review` で判断に写す。`REMOVE` はすぐ `remove`、`AGENT` は `agent:` の作業を済ませてから `remove`。

### 2.6 記録が来たらすぐ始める（見張り）

人が「来たらすぐ対応して」「見張って」と言ったときは `watch.md` の手順で `scripts/watch-inbox.mjs` を背景で動かし、`NEW` の行で手順 0 に戻る。

## 3. 報告の形

太字の見出しで、**結果 / あなたの判断が要るもの / 実機で見てほしい点**。メモがあれば最後に「メモにあった未対応の指摘」。毎回の最後に、未解決の「返事待ち」の一覧を累積して付ける。

件数が多いときは、報告を **HTML 1 枚**（`{tmp}/<名前>/report.html`）にする。最初に見える部分は「結果の表（id・要旨・種類・結果）」と「あなたの判断が要るもの」だけにし、変更したファイル・確認コマンドの出力・判断した点は `<details>` に畳む。人が項目にコメントを返せるよう、`references/setup/web/single-html.md` のフィードバックを付けてもよい。

## 4. 補助のファイル

- `subagent-prompt.md`: サブエージェントへのプロンプトのひな形（実装・調査・設計）。起動の前に読む。
- `full-check.md`: ループを抜けたあとの全体チェックと「修正の回」。手順 7 で読む。
- `lessons.md`: 実際に起きた落とし穴と対処。初回と、挙動がおかしいときに読む。

## 5. まだ無いもの

- **自動で始める**: 見張り（§2.6）は人の指示か、ループの待ちで動かす。会話の外で勝手に始める（`SessionStart` の hook・スケジュール）は未実装。
- **取り込み元を増やす**: Inbox に直接書けない環境（モバイル実機など）から、Issue トラッカー・Slack・共有フォルダの記録を `putEntry` で Inbox に入れる。
- **ステータス欄**: 持たない。archive の対応メモと履歴の「結果」で足りる想定。
