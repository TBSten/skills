# サブエージェントのプロンプトのひな形

参照実装の運用 skill のサブエージェント用プロンプト【実績】を汎用化したもの。`Agent` ツールで `subagent_type: general-purpose`（または `claude`）、`model: sonnet`、effort は実装・調査が `high`、簡単な確認が `medium`。`{...}` を埋めて渡す。サブエージェントは会話の文脈を知らないので、ここに書かないことは伝わらない。

## 穴埋めの一覧

| 穴 | 内容（参照実装の例は括弧） |
|---|---|
| `{担当名}` | 領域の短い名前（一覧カード） |
| `{app}` | アプリ名とリポジトリのルート・git 管理の有無（<アプリ名>、`<リポジトリのルート>`、git 管理の有無） |
| `{記録の参照一覧}` | 記録の参照（パス・URL・Issue 番号）を 1 行ずつ。**Sink が読める形で**（`<Inbox>/yymmdd-xx.md`） |
| `{各件の要約}` | 件ごとに 1〜2 行（文と位置。オーケストレータの解釈） |
| `{意図}` | 文の意味と意図。曖昧なら「あなたが決めて、報告に書く」 |
| `{読むもの}` | 正本 docs の関連の節、ソースのパス（`CLAUDE.md`、アプリの `README.md`） |
| `{確認コマンド}` | テスト・型検査・ヘッドレス確認（`cd <アプリのディレクトリ> && npm run check`） |
| `{禁止}` | `references/loop/loop.md` §0 の「触ってはいけないもの」 |
| `{関係するメモ}` | 対象のページのメモのパス（`references/loop/loop.md` §2.4。無ければ「なし」） |
| `{同時に動いている作業}` | どの領域を誰が編集しているか（共有ファイルの衝突に注意）。なければ「なし」 |
| `{作業名}` / `{tmp}` | 作業用ディレクトリの名前（`.local/tmp/{作業名}/` にスクリーンショット・設計メモ） |

## 共通部分（3 種類すべてに入れる）

```
あなたは「{担当名}」の担当です。{app}。

## 対象のフィードバック
{記録の参照一覧}
記録は長い（最大 100KB）。必ず全部読むこと。分割して読んでよい。GUI のフィードバック形式なら「フィードバックの文」「選んだ位置」「スクリーンショット」（記録に書いてある参照を Read で見られる。window は選んだ要素が枠で囲まれている）「画面に出ている情報」「ログ」を読む。
{各件の要約}
記録には frontmatter のある新形（schema 1。kind・source・stale・dirty など）と、無い旧形がある。無い項目は「情報が無い」だけで異常ではない。`stale: true` は記録のあとにソースが変わったこと。位置・文言は今のソースとずれているかもしれないので、まず履歴（git log など）で、すでに直っていないかを確かめる。

## 関係するメモ
{関係するメモ}
メモは、利用者がページを読みながら書き溜めた考え。記録の意図の手がかりとして読む（末尾の HTML コメントの JSON は読まなくてよい）。メモは書き換えない・移さない。記録とメモが食い違ったら、新しいほう（各メモの「最終更新」と記録の created）を優先し、報告に両方を書く。記録に無いメモだけの指摘は直さず、報告に「メモにあった未対応の指摘」として並べる。

## 意図
{意図}

## 最初に読むもの
{読むもの}

## 同時に動いている別の作業
{同時に動いている作業}
共有ファイル（{共有ファイルの例}）は、書き込む直前に必ず読み直し、他の人の変更を消さないこと。変更は最小にし、できれば新しいファイルに切り出す。

## テストと確認
- {確認コマンド}。他の Agent の作業途中の変更で落ちることがある。落ちたら自分の変更に由来するかを切り分ける。他に由来するなら直さず報告だけ。揺れるテストは、少し置いて単独で再実行し、再現率を報告する。
- 見た目の確認は、ヘッドレスのスクリーンショット（偽物・一時データ。実データが写らないこと）。{tmp}/{作業名}/ に置き、Read で見て確認する。

## 禁止
{禁止}
- 置き場の記録（{記録の参照一覧}）の移動・削除・変更（archive はオーケストレータだけ）。メモ（{関係するメモ}）の変更・移動・削除。
- $TMPDIR の削除、他のプロセスの kill（自分が起動したプロセスの終了はよい）。
- 大きな設計変更の実装。必要なら実装せず、選択肢と推奨を報告に書く。小さな判断は、既存の流儀に最も合う形で進め、「判断した点」に書く。

## 報告の形式（日本語、簡潔に）
フィードバックの一覧と結果 / 設計の要点 / 変更したファイル / テスト結果 / スクリーンショットのパス / 判断した点 / 記録とメモが食い違った点と、メモにあった未対応の指摘 / ユーザの確認が要る点 / 実機で見てほしい点
```

## 種類別の追加部分

### 実装型（共通部分のあとに足す）

```
## 種類: 実装
要望を実装してください。設計は任せます。決めた内容は {正本} の該当の節に書き、報告にも書いてください。元のフィードバックの ID と文（「<日付> ユーザーのフィードバック <id>「…」」の形）も書いてください（後から由来をたどれるように。参照実装の流儀）。既存のテストの流儀に合わせて、挙動を確かめるテストを足してください。
```

### 調査型（共通部分のあとに足す）

```
## 種類: 調査（質問・確認）
このフィードバックは質問・確認です。文が「（書いていません）」の場合は、位置の要素・画面に出ている情報・ログから、ユーザが何を心配しているかを読み取ってください。
1. ユーザの質問（または心配）を 1 文で言い直す。
2. 原因と現状を、コード・設定・ログの根拠つき（ファイルと行）で答える。
3. まず「開発起動で、古いプロセスが動いたまま画面側だけ再読み込みされた食い違い」を疑う（新しい設定キー・IPC の戻り値を知らない）。その場合は「再起動で直る」と明記し、起動中のプロセスと画面の版のずれを検知できるかも検討して報告する。
4. 本当に問題があれば、最小の変更で直し、テストを足す。大きな変更が要るなら直さず、選択肢と推奨を報告する。
```

### 設計だけ（読み取りのみ）型（共通部分の「テストと確認」の代わりに）

```
## 種類: 設計だけ（読み取りのみ）
ソース・docs・設定は変更しないでください（読むだけ）。書いてよいのは {tmp}/{作業名}.md だけです。次を書いてください。
- 現状と問題（根拠のファイルと行）
- 影響範囲
- 設計案（2〜3 案）と、それぞれの長所・短所
- 推奨とその理由
- 実装を分ける場合の単位（領域ごと。並列にできるか）
- ユーザに決めてほしい点
報告には、メモのパスと、上の要点を 10 行以内で書いてください。
```
