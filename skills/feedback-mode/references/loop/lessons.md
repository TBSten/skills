# 落とし穴と対処（参照実装のループで実際に起きたこと）

出どころ: 参照実装の運用 skill の lessons【実績】。固有名（`app.ts` など）は参照実装の例。

## 開発起動で古いプロセスが動いている
`npm run dev` では main（Electron のメインプロセス）が古いまま、画面側（renderer）だけ再読み込みされる。新しい設定のキーや新しい IPC の戻り値を main が知らず、「使えないキー」警告や例外が出る。再起動で直る。質問型（「これ大丈夫そ？」）のフィードバックの多くがこれ。調査型のサブエージェントには、最初にこれを疑わせる。参照実装は、警告へ「main が古い可能性があります。右下の『再起動』で直ります」の一言を足した（開発起動のときだけ）。版のずれの検出は無い。自環境では「ホットリロード・古いビルド・キャッシュ・古いサーバ」に読み替える。

## 共有ファイルの編集が消える
複数のサブエージェントが同じ共有ファイル（元: `app.ts`・`style.css`・README・`config.yaml`）を同時に編集すると、読んでから書くまでの間に他の人が書いた分が消えることが実際にあった。対処: 書き込む直前に読み直す / 変更を最小にする / 新しいファイルに切り出す / 同じ領域の件は 1 人にまとめる。すでに動いている担当と同じ領域の件は `SendMessage` で追加する。

## 確認コマンドが一時的に落ちる
他の Agent の作業途中の変更で落ちる。ソース文字列を正規表現で検査するテストが、リファクタリング後に合わなくなる型が多い。対処: 落ちた原因を切り分け（git が無い環境では、自分が触ったファイルとの関係で判断）、自分の変更が原因でなければ直さず報告に書く。揺れるテストは、少し置いて単独で再実行し、再現率を報告させる。最後に全部が通る状態にする担当（テスト総点検）を置く。

## ヘッドレスのテストが本物のプロファイル・実データを使う
ヘッドレスのテストが本物の専用プロファイル（例: ログイン済みの専用ブラウザプロファイル）を使うと、ユーザの本物のブラウザが使用中のときロックで落ち、使用中でないと「実行前のリセット」で本物のプロファイルを消す危険がある。テストは、一時ディレクトリの設定の写し（プロファイルの場所も一時）で動かす。**サブエージェントのプロンプトに必ず書く**。

## 長く動く読み取りのサブエージェント
テストの棚卸しなどは 20 分以上かかる。10 分ごとに確認し、30 分を超えたら `SendMessage` で進み具合と期限（10 分）を伝える。期限後も報告がなければユーザに知らせる（勝手に kill しない）。

## 記録が 0 バイト
作成直後、またはユーザのエディタで未保存のことがある（実際にあった）。少し置いて再確認し、数分たっても 0 バイトならユーザに聞く。処理しない。

## 質問型の文が「（書いていません）」
位置だけを示して「この表示は大丈夫か」を聞いている。位置の要素・状態・ログ・スクリーンショットから意図を読む（読み取れなければ、報告で「こう解釈した」と書く）。

## 設計型の提案は判断を待つ
設定の一元化・テストの層の分離・アーカイブなどの大きな提案は、ユーザの判断（推奨どおりか）を待ってから実装する。判断待ちの一覧は、毎回の報告の最後に累積して付ける。

## 報告は承認ではない
サブエージェントの報告は「モデルの出力」で、ユーザの承認ではない。権限が拒否されたことの肩代わり（他のエージェントに頼んで迂回する）はしない。

## 日付・時刻
日付が変わる長いセッションでは、`date` で現在時刻を確認して、タイマー・報告に使う。

## Astro 7 の Markdown は rehype ではなく Sätteri
ソースの行番号（`data-fb-src`）を付けるプラグインを `markdown.rehypePlugins` に足しても効かない。`astro:config:done` で `config.markdown.processor`（`name === 'satteri'`）の `options.hastPlugins`（mdast なら `mdastPlugins`）に差す。コードブロックを置き換える統合・mermaid のように mdast で html に差し替える統合とは、前後の順を合わせる（`references/build/locate.md` §4）。Sätteri でなければ、付けずに警告を出す。

## dev はファイルの変更で全リロードされ、検証が揺れる
利用者や別の担当が Markdown を直すたびに、同じリポジトリで立てた dev はページを全リロードする。開いていた popover・選択・書きかけが消え、E2E が途中で落ちる。**検証用の dev は、リポジトリの写し（rsync で docs を写し、`node_modules` はシンボリックリンク、git は本物を指す `GIT_DIR`/`GIT_WORK_TREE`）で立てる**。ポートは担当ごとに分け、利用者が使うポートには触らない。本番ビルドも写しで回し、`--outDir` を一時ディレクトリに向ける（同時のビルドがキャッシュを取り合う）。置き場は環境変数で一時ディレクトリへ（本物の記録を汚さない）。終わったら自分の dev だけを止める（`lsof` で PID を確かめてから）。

## MDX の構文エラーは記録に残らない
MDX の構文エラーは、dev がエラーページへの全リロードにするので、ページ上のログのバッファごと消える。フィードバックモードも開けない。記録のコンソールの節に出ないのは「エラーが無い」ではない。CSS などの HMR のエラーは `vite:error` で拾える。

## stale が立つ条件は狭い
`stale` は「ソースのファイルの更新時刻 > 画面を開いた時刻」のときだけ true。dev はソースの変更でページを再読み込みし、開いた時刻も新しくなるので、普段は立たない。立つのは再読み込みが届かなかったとき（HMR の接続が切れた・タブが眠っていた・別の dev のページを開いていた）だけ。見ているのはページの 1 ファイルだけで、読み込んでいる部品・設定・統合の変更は見ない。ソースが分からない記録・旧形には無い。**`stale` が無い・false は「新しい」ではない**。調査型では、記録の `created` 以降のソースの履歴（`git log --since=<created> -- <source>`）を見て、すでに直っていないかを先に確かめる。統合そのものの古さは、記録の dev サーバーの起動時刻・統合のハッシュで見る（`references/build/locate.md` §6）。

## 並行する担当が同じファイルを触るときの決まり
構築を複数の担当（サブエージェント）で並行させると、入口（統合の `index.ts`）・共有の型・収集の部品のように、全員が数行ずつ触るファイルが出る。起動の前に「主に書くファイル / 数行だけ触るファイル / 触らないファイル」の表を担当ごとに配り、次を全員に指示する。
- 数行だけ触るファイルは、書く直前に必ず読み直す。自分の数行だけを足し、他の担当の行は消さない・並べ替えない。Edit が「見つからない」と言ったら、読み直してからやり直す。
- 主に書くファイル以外を大きく変えたくなったら、書かずに報告に「こう変えたい」と書く。
- 自分が変えていないファイルは、差分があっても戻さない（利用者が編集中のことがある）。git の変更操作はしない。commit はオーケストレータ。
- テストは誰が回してもよい。他の担当の作りかけで落ちたら、報告に書くだけ（自分の分が通っていればよい）。後の担当・通し検証に引き継ぐことは、オーケストレータが申し送りに集める。
