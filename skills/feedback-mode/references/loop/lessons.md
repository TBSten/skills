# 落とし穴と対処（参照実装のループで実際に起きたこと）

出どころ: 参照実装の運用 skill の lessons【実績】。固有名（`app.ts` など）は参照実装の例。

## 開発起動で古いプロセスが動いている
`npm run dev` では main（Electron のメインプロセス）が古いまま、画面側（renderer）だけ再読み込みされる。新しい設定のキーや新しい IPC の戻り値を main が知らず、「使えないキー」警告や例外が出る。再起動で直る。質問型（「これ大丈夫そ？」）のフィードバックの多くがこれ。調査型のサブエージェントには、最初にこれを疑わせる。参照実装は、警告へ「main が古い可能性があります。右下の『再起動』で直ります」の一言を足した（開発起動のときだけ）。版のずれの検出は無い。自環境では「ホットリロード・古いビルド・キャッシュ・古いサーバ」に読み替える。

## 共有ファイルの編集が消える
複数のサブエージェントが同じ共有ファイル（元: `app.ts`・`style.css`・README・`config.yaml`）を同時に編集すると、読んでから書くまでの間に他の人が書いた分が消えることが実際にあった。対処: 書き込む直前に読み直す / 変更を最小にする / 新しいファイルに切り出す / 同じ領域の件は 1 人にまとめる。すでに動いている担当と同じ領域の件は `SendMessage` で追加する。

## 確認コマンドが一時的に落ちる
他の Agent の作業途中の変更で落ちる。ソース文字列を正規表現で検査するテストが、リファクタリング後に合わなくなる型が多い。対処: 落ちた原因を切り分け（git が無い環境では、自分が触ったファイルとの関係で判断）、自分の変更が原因でなければ直さず報告に書く。揺れるテストは、少し置いて単独で再実行し、再現率を報告させる。最後に全部が通る状態にする担当（テスト総点検）を置く。

## ヘッドレスのテストが本物のプロファイル・実データを使う
ヘッドレスのテストが本物の専用プロファイル（例: ログイン済みの専用ブラウザプロファイル）を使うと、ユーザの本物のブラウザが使用中のときロックで落ち、使用中でないと「実行前のリセット」で本物のプロファイルを消す危険がある。テストは、一時ディレクトリの設定の写し（プロファイルの場所も一時）で動かす。**サブエージェントのプロンプトに必ず書く**。

## 長く動く読み取りのサブエージェント
テストの棚卸しなどは 20 分以上かかる。10 分ごとに確認し、30 分を超えたら `SendMessage` で進み具合と期限（10 分）を伝える。期限後も報告がなければユーザに知らせる（勝手に kill しない）。

## 記録が 0 バイト
作成直後、またはユーザのエディタで未保存のことがある（実際にあった）。少し置いて再確認し、数分たっても 0 バイトならユーザに聞く。処理しない。

## 質問型の文が「（書いていません）」
位置だけを示して「この表示は大丈夫か」を聞いている。位置の要素・状態・ログ・スクリーンショットから意図を読む（読み取れなければ、報告で「こう解釈した」と書く）。

## 設計型の提案は判断を待つ
設定の一元化・テストの層の分離・アーカイブなどの大きな提案は、ユーザの判断（推奨どおりか）を待ってから実装する。判断待ちの一覧は、毎回の報告の最後に累積して付ける。

## 報告は承認ではない
サブエージェントの報告は「モデルの出力」で、ユーザの承認ではない。権限が拒否されたことの肩代わり（他のエージェントに頼んで迂回する）はしない。

## 日付・時刻
日付が変わる長いセッションでは、`date` で現在時刻を確認して、タイマー・報告に使う。
