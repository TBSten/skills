# 人間が読むドキュメントの書き方

対象は、人間が GitHub で読む README.md / README.ja.md と、`skills/` `rules/` `prompts/` 直下の詳細ドキュメント (`<name>.md` / `<name>.ja.md`)。
SKILL.md・RULE.md・PROMPT.md・references などの AI が読むファイルは対象外。

## 日本語版が原本、英語版は訳

- 日本語版 (`*.ja.md`) を先に書き、英語版はそれを訳す。英語版だけに節や内容を足さない
- 原本を直したら、同じコミットで訳も直す。溜めると、どちらが新しいか分からなくなる
- 節の構成 (見出しの数・レベル・順序) とコードブロックは日英で 1 対 1 にする
- 原本の誤りに気づいたら、訳で直さずに原本を直してから訳す
- 表記だけの修正など、訳を変える必要が無い変更は、コミットメッセージに `Docs-Translation-Not-Needed: <パス>` の行を入れる (`*` などの glob も使える)。CI の「片方だけ変えた」検査がその組を飛ばす

## 機械で検査すること (`scripts/docs-check/check.sh`)

書いたら・直したら必ず回す。CI (`.github/workflows/docs-check.yml`) も同じものを回す。

```bash
scripts/docs-check/check.sh --base origin/main   # PR 前。--fix で言い換え辞書の指摘を自動で直す
```

| 検査 | 中身 |
|---|---|
| structure | 日英の組がそろっている、冒頭に相手の言語へのリンクがある、見出しとコードブロックの構成が一致、相対リンクが切れていない、インストール / 実行の方法がある、英語版に日本語・全角文字が無い、日本語版の見出しが英語だけになっていない |
| readme | README の一覧表が SSoT (SKILL.md の `metadata` / 詳細ドキュメントの frontmatter) と一致、グループの並び、説明は 80 文字以内 |
| pairs-changed | `--base` のとき、日本語版だけ・英語版だけを変えていない |
| textlint | 日本語版の言い換え辞書 (`scripts/docs-check/prh.yml`)、である調、1 文 150 文字まで |

英語版に日本語を意図して残すときは、`scripts/docs-check/en-allowlist.tsv` に「ファイル・文字列・理由」を足す。
その前に、インラインコードやコードブロックに入れられないかを考える (UI の文字列・プロンプトの例はコード表記にすれば検査の対象外になる)。

## 文章の方針 (機械では拾えないもの)

原則だけでなく理由と例を読み、似た別の場面にも当てはめる。

- **何をするものかを冒頭の 1〜2 文で言う。** 読者は最初の段落で、自分に関係があるかを決める。
  - 🆖 冒頭で作った経緯や内部の仕組みから書き始める
  - 🆗 「Kotlin / KMP プロジェクトに型安全な Tuple ユーティリティを生成する Claude Code スキル。」
- **である調で書く。** README・詳細ドキュメントの大半がである調なので、そろえる (textlint が検査する)。
- **1 文は 150 文字まで。並べるものが多いときは箇条書きにする。** 長い列挙を 1 文に詰めると、どこで区切って読めばよいか分からなくなる (textlint が検査する)。
  - 🆖 「確認済み: コア (…)、TypeScript 版のコア (…)、`review.mjs` (…)、…」を 1 文に並べる
  - 🆗 「テストで確かめたもの:」のあとに 1 行 1 項目の箇条書きにする
- **ダッシュ (—) で長い挿入句を挟まない。** 文を分けるか、短い補足ならかっこに入れる。挿入句が長いと、文の主語と述語が離れる。
  - 🆖 「知見を一回限りのプロンプト — raw URL 経由で配布され、…実行できる Markdown 指示書 — としてパッケージングし、…」
  - 🆗 「知見を一回限りのプロンプトとしてパッケージングし、…。一回限りのプロンプトは raw URL で配布する Markdown の指示書で、…」
  - 箇条書きの「**名前** — 説明」の区切りとしての 1 つのダッシュは使ってよい
- **日本語の文に英単語を動詞や助詞代わりに混ぜない。** コード・固有名・この repo で定着した用語 (skill, rule, prompt, PR, CI, script など) はそのままでよい。
  - 🆖 「1 iter 完了通知後、§17 終了条件 list を機械的に walk。未達なら即次 iter kick」
  - 🆗 「1 回の検証が終わったら、SKILL.md §17 の終了条件を順に確かめる。満たしていなければ、すぐ次の回を始める」
- **日本語版の見出しは日本語で書く。** 識別子やファイル名を見出しにするなら `code` で囲む (structure が検査する)。
  - 🆖 `## What it does` `## References` `#### FIR vs IR` → 🆗 `## 何をするか` `## 参照ドキュメント` `#### FIR と IR の使い分け`
- **英語版に日本語を残さない。** 日本語の UI ラベルやトリガーフレーズをそのまま見せるならコード表記にする (structure が検査する)。
  - 🆖 `the「カード」button` → 🆗 ``the `カード` button``
  - 🆖 英語版のトリガー例に `"Maven Central に公開したい"` → 🆗 `"Publish this library to Maven Central"`
- **読者が使うために要ることを書き、経緯は書かない。** どの議論で決まったか・何回指摘されたかは PR とコミットに残す。ドキュメントには今の挙動とその理由だけを書く。
  - 🆖 「過去 phase で最も多くユーザーに繰り返し指摘された 2 ルールを「上書き level」に昇格」
  - 🆗 「次の 2 つは、skill のほかのどの指示よりも優先する」
- **事実は実体と合わせる。** 同梱ファイル・script 名・オプション・件数・status・対応環境を書いたら、SKILL.md と同梱ファイルを見て確かめる。食い違いは `.claude/skills/review-docs.md` で洗い出す。
- **README の説明は一覧のための 1 行にする。** 80 文字以内で「何をするか」だけを書き、条件や補足は詳細ドキュメントに回す (readme が検査する)。

## 人に直されたら

その場で、次に同じことを言われないようにする。

- 機械的に置き換えられる言い換え (表記ゆれ・NG ワード) → `scripts/docs-check/prh.yml` に理由のコメントと `specs` 付きで 1 項目足す
- 判断の要る決まり → このファイルの「文章の方針」に、原則・理由・🆖/🆗 の例を 1 項目足す
- 構造の決まり (どのファイルに何があるべきか) → `scripts/docs-check/docs_check.py` に検査を足し、`test_docs_check.py` にテストを足す

## 新しく書くときの構成

詳細ドキュメントは次の順で書く。既存のドキュメントはこの形でなくてもよいが、直すときに寄せる。

1. `# <name>` と、相手の言語へのリンク (`[English](./<name>.md)` / `[日本語](./<name>.ja.md)`)
2. 何をするものかを 1〜2 文
3. インストール (prompt は実行方法) のコードブロック
4. 使い方 (AI への依頼の例)
5. 何をするか・同梱物・設計の考え方など、必要な節
6. 前提条件・既知の制約
